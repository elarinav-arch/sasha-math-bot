# Мур-математика: командный режим для нескольких детей

**Дата:** 2026-08-16
**Статус:** утверждено

## Цель

Бот сейчас жёстко заточен под одного ребёнка (Александру): один `CHILD_CHAT_ID`,
один `progress.json` на всех. Нужно расширить его на команду детей (может вырасти
до нескольких десятков), которые тренируются **одновременно, в одном общем боте**,
и мотивируются **сотрудничеством, а не соревнованием друг с другом**.

Кошачья коллекция и игровой стиль (фразы, юмор, реалистичные фото пород) остаются
без изменений. Telegram Mini App — явно вне рамок этой спеки, обсуждается отдельно
позже.

## Ключевые решения

- **Одна команда, один бот.** Не отдельные копии бота на семью — все дети видят
  друг друга как одну команду внутри существующего `@RoboPetsMathBot`.
- **Одно расписание на всех** — те же три окна: 14:00 / 17:00 / 19:00 по Кипру.
- **Саморегистрация через код-приглашение** (`/join КОД`), не открытая регистрация —
  бот публичный и речь о детях, поэтому нужен барьер от случайных/посторонних.
- **Личный прогресс остаётся личным.** У каждого ребёнка — свой собственный Лейтнер,
  свои звёзды, свой шанс на карточку за сессию (3⭐ гарантия / 2⭐ 50% / 1⭐ мимо),
  свой бонусный раунд, своя коллекция из 60 котиков, своя дневная серия (streak).
  Existing одиночная механика **не переписывается** — просто работает параллельно
  для N детей вместо одного.
- **Командный слой — только на уровне недели.** Раз в неделю (воскресенье вечером)
  считается общий результат команды; при достижении цели — общий трофей всем.
  Никаких персональных сравнений («X обогнал Y») нигде не показывается.
- **Отчёты — пока только Елене**, один сводный отчёт по всей команде (не по
  отдельным семьям).

## Данные

Текущий `Progress` (facts/days/streak/cards/totalStars) — это прогресс ОДНОГО
ребёнка. Он остаётся почти как есть, но переименовывается в `ChildProgress` и
кладётся в новую обёртку:

```ts
interface ChildProgress {
  chatId: number;
  name: string;           // Telegram first_name на момент /join
  joinedAt: string;       // ISO-дата регистрации
  facts: Record<string, FactProgress>;
  days: DayRecord[];
  streak: number;
  cards: string[];
  totalStars: number;
}

interface WeeklyGoal {
  weekStart: string;      // YYYY-MM-DD понедельника текущей недели
  starsByChild: Record<number, number>;  // накопленные за неделю звёзды, по chatId
  trophyAwarded: boolean;
}

interface TeamState {
  children: Record<number, ChildProgress>;  // ключ — chatId, для O(1)-поиска при маршрутизации
  weeklyGoal: WeeklyGoal;
  trophyCards: string[];  // id полученных командой трофейных карточек (кумулятивно)
}
```

`progress.json` теперь хранит `TeamState` вместо одного `ChildProgress`. Код-приглашение
живёт в GitHub Secret `TEAM_INVITE_CODE` — **не в репозитории** (репозиторий публичный,
секрет в закоммиченном файле кто угодно прочитал бы из истории git).

## Регистрация

- Ребёнок пишет боту `/join КОД` в любое время, пока идёт обработка (окна тренировок +
  внутренний резервный cron — то же временное покрытие, что уже есть).
- Верный код → создаётся `ChildProgress` с `name` из `message.from.first_name`,
  приветственное сообщение «Добро пожаловать в команду!». Неверный код → вежливый
  отказ без деталей (не подсказываем, что именно не так, чтобы не облегчать перебор).
- Первая полноценная тренировочная сессия — на ближайшем следующем окне после
  регистрации. Не пытаемся подключать ребёнка «на лету» посреди уже идущей рассылки —
  усложнение не оправдано для MVP.
- Уже зарегистрированный ребёнок, повторно написавший `/join`, получает мягкое
  «ты уже в команде!» без побочных эффектов.

## Архитектура: параллельные тренировки без гонки за offset

Telegram `getUpdates` — long polling с **одним общим offset на весь бот**, не на
пользователя. Если каждая детская сессия будет сама вызывать `getUpdates` со своим
offset — сессии будут гоняться за одни и те же обновления и путать друг друга.

Решение: **один общий `TelegramPoller`** на весь запуск джобы.

- `TelegramPoller` — единственный объект, который реально дёргает `getUpdates` в
  цикле и хранит единый offset.
- У него есть метод регистрации ожидания: `waitFor(chatId, timeoutMs): Promise<string | null>`.
  Внутри — `Map<chatId, (text: string) => void>` с резолверами; когда очередной
  `getUpdates` возвращает сообщение от `chatId`, диспетчер ищет резолвер по этому
  `chatId` и вызывает его (или откладывает, если для этого чата сейчас никто не ждёт).
- `TelegramIO` (уже существующий интерфейс `send`/`waitForReply`/`extendDeadline`)
  остаётся ровно таким же по контракту, но его реализация под каждого ребёнка
  становится тонкой обёрткой вокруг общего `TelegramPoller.waitFor(childChatId, ...)`
  вместо собственного цикла опроса. `runSession`, вся игровая логика сессии —
  **не меняются**: они как ждали ответ через `await io.waitForReply(...)`, так и ждут.
- `main()` вместо одной сессии на один `chatId` запускает `Promise.all` по всем
  зарегистрированным детям (плюс отдельно обрабатывает входящие `/join` от
  незарегистрированных чатов) — все тренируются в одном процессе одновременно.

Рассмотренная и отклонённая альтернатива: раздельный GitHub Actions job на ребёнка
(`strategy: matrix`). Та же проблема с общим offset никуда не девается (offset общий
на **токен бота**, а не на job), а вдобавок десятки параллельных job пытались бы
одновременно коммитить в один `progress.json` — конфликты гарантированы. Общий
диспетчер внутри одного процесса решает обе проблемы разом: один offset, один
`git commit` в конце.

## Личная экономика (без изменений в логике)

Всё, что уже работает у Александры — `starsForSession`, `cardChance`/`rollSessionCard`,
`awardBonusCard`, `dayParticipated`/`finishDay` (личный streak), `pickNewCard` (60 котов,
55/30/15 по редкости) — используется **как есть**, по одному разу на каждого ребёнка,
над его собственным `ChildProgress`. Новых наградных механик на уровне сессии/дня
не вводится.

## Командная экономика: недельный трофей

- В воскресенье вечером (после обычных вечерних сессий всех детей) — отдельный шаг
  подведения недели.
- «Активный на этой неделе» — ребёнок с `sessions > 0` хотя бы в один из дней недели.
  Неактивные не считаются ни в числитель, ни в знаменатель цели — не портят результат
  остальным и не обесценивают его для маленькой активной команды.
- Цель = `20 × количество активных детей`. Фактический результат = сумма их звёзд
  за неделю (уже трекается per-day в `ChildProgress.days`, дополнительно суммируем
  в `WeeklyGoal.starsByChild` по ходу недели, чтобы не пересчитывать historical
  `days` каждый раз).
- Цель достигнута → всем зарегистрированным детям (не только активным — команда
  есть команда) уходит сообщение с трофейной карточкой из отдельного пула
  `TROPHY_CARDS` (не пересекается с обычными 60 котиками; ~8–10 карточек, тематически
  «величественные коты» — снежный барс, огненный лев и т.п.). Каждая трофейная
  карточка — одноразовая: если у команды уже есть все имеющиеся трофеи, просто
  тёплое поздравление без новой карточки (аналогично `pickNewCard` при пустом пуле).
- Цель не достигнута → тёплое сообщение без имён и без цифр по конкретным детям
  («Почти-почти! На следующей неделе точно получится 💪»), `WeeklyGoal` обнуляется
  на новую неделю.
- Реализация: новая функция `finishWeek(team, now)` в `rewards.ts`, вызывается
  из `main()` только когда текущий вечерний прогон приходится на воскресенье
  (по кипрской дате).

## Сообщения и тон

- Никаких упоминаний «ты обогнал(а) X» или явных рейтингов по именам.
- Общий недельный итог — только агрегат («команда набрала N из M ⭐»), без разбивки
  по детям.
- Личные сообщения (похвала, подсказки, итог сессии) — без изменений, обращены
  к конкретному ребёнку по имени, как сейчас у Александры.

## Расписание и деплой

- `train.yml` не меняется по частоте (внешний cron-job.org + внутренний резервный
  GitHub cron — та же схема), меняется только то, что каждый запуск теперь
  обрабатывает **всех** зарегистрированных детей параллельно вместо одного
  захардкоженного `CHILD_CHAT_ID`.
- Секреты: `CHILD_CHAT_ID` и `PARENT_CHAT_ID` заменяются на `TEAM_INVITE_CODE`
  (для `/join`) и `PARENT_CHAT_ID` остаётся (сводный отчёт Елене). `CHILD_CHAT_ID`
  как секрет больше не нужен — Александра уже зарегистрирована в `progress.json`
  как первый ребёнок команды (миграция её текущего `Progress` в первую запись
  `children`).

## Обработка ошибок и краевые случаи

- Ребёнок написал `/join` с неверным кодом несколько раз подряд — не блокируем,
  просто не регистрируем; race для оффлайн бота не критичен.
- Двое детей отвечают одновременно в одном `getUpdates`-батче — диспетчер обрабатывает
  оба сообщения из одного ответа `getUpdates`, раздавая по `chat.id`; порядок
  не важен, так как резолверы независимы по чатам.
- Ребёнок регистрируется, но GitHub Actions падает до `git push` (как раньше) —
  как и сейчас, следующий тик подхватит несохранённое состояние заново (ничего
  не коммитится, если джоба не долетела до конца).
- Один ребёнок «завис» без ответа (укладывается в свой персональный таймаут) —
  не блокирует остальных: `Promise.all` ждёт каждого независимо, диспетчер продолжает
  раздавать сообщения другим, пока не истечёт время самого долгого ожидающего.
- Ребёнок регистрируется в середине недели (например, в субботу) — считается
  «активным» при первой же сессии и участвует в пороге наравне со всеми
  (`20 × активные`), даже если физически успел позаниматься 1 раз. Сознательное
  упрощение для MVP: нет пропорционального снижения порога по дням в команде.
  Если станет ощутимой проблемой на практике (реальные жалобы на нечестность) —
  добавим пропорцию отдельным изменением.

## Тестирование

- `TelegramPoller` — юнит-тесты на маршрутизацию по `chat.id` (в том числе несколько
  сообщений в одном батче `getUpdates`, сообщение от незарегистрированного чата не
  вызывает резолвер ни для кого).
- `finishWeek` — тесты на: цель достигнута/не достигнута, порог масштабируется по
  числу активных детей, неактивные не в счёт, трофей не дублируется, пустой
  `TROPHY_CARDS` пул обрабатывается как в `pickNewCard`.
- `/join` — тесты на верный/неверный код, повторная регистрация, `first_name`
  корректно попадает в `ChildProgress.name`.
- Существующие тесты личной экономики (`rewards.test.ts` и т.д.) не меняются —
  логика, которую они проверяют, не меняется.

## Вне рамок (YAGNI)

- Telegram Mini App — отдельная спека позже.
- Персональные чаты родителей по ребёнку — все отчёты пока идут только Елене.
- Открытая/динамическая ротация кода-приглашения (смена кода, множественные коды
  на разные группы) — один статичный код на команду, меняется вручную через
  обновление секрета при необходимости.
- Мгновенное подключение к уже идущей сессии сразу после `/join` — ждём следующего окна.
- Командные ежедневные (не только еженедельные) награды.
